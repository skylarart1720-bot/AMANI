# Account security and operational monitoring

Sign in to the moderator dashboard and open **Account security**. Enter your current staff password or existing Railway Super Admin token to start enrollment. Add the displayed key to a time-based authenticator, then confirm its six-digit code within ten minutes. Save the eight recovery codes securely: they are displayed once and each works once. The database encrypts authenticator secrets with the existing chat encryption key and stores hashes of recovery codes.

After activation, sign in with your normal credential plus an authenticator or recovery code. Token-only Super Admin requests are rejected while MFA is enabled. Enrollment and disabling MFA revoke that account's sessions. New sessions expire after one hour. Codes cannot be reused; keep device time synchronized. Generating new recovery codes invalidates the old set. MFA is optional until each account enrolls; deploying does not enroll or lock out the owner.

Super Admin can reset a staff member's MFA from **Staff accounts**, which also revokes their sessions. If Super Admin loses the authenticator and all recovery codes, an authorized operator with access to the Railway API container and persistent volume can run, from `apps/orchestrator`, `python -m src.security reset-super-admin-mfa --data-dir /data --confirm` (use the actual mounted data directory). This is audited and revokes Super Admin sessions. Then sign in with the existing Railway token and enroll again. There is no public recovery bypass. Preserve both existing `ADMIN_API_TOKEN` and `CHAT_ENCRYPTION_KEY` during deployments and restores.

Super Admin's **Service monitoring** checks scanner and gateway health, storage space and encrypted backup archive freshness every 60 seconds. AI status comes from real consented requests; monitoring spends no AI credits. Provider quota exhaustion, rate limits and rejected credentials have distinct diagnostics. Two consecutive failures open one incident; healthy recovery closes it. Acknowledging an incident records who reviewed it without claiming recovery.

Set Railway `AMANI_ALERT_WEBHOOK_URL` to an HTTPS operational alert receiver and optionally `AMANI_ALERT_WEBHOOK_TOKEN` for Bearer authentication. Payloads contain incident ID, service, state, generic diagnostic, creation and recovery timestamps only. Delivery retries up to five times with increasing delay; failed deliveries can be retried from the dashboard. Without a receiver, alerts remain visible in the dashboard. Do not configure a receiver that exposes alerts publicly.

Set `AMANI_BACKUP_DIR` to the directory populated by your encrypted backup schedule. Monitoring checks whether an `.amani-backup` file was written within 24 hours; it does not create archives or prove a restore works. Schedule off-host backups and test restoration separately. Restoring preserves enrolled MFA but revokes staff and Super Admin sessions.

API `/health` returns 503 when the database cannot be read. Use an external uptime monitor on the public site, dashboard and API health endpoints: the in-process checker cannot alert while the API itself is stopped. Organisation isolation, external alert receiver configuration and automated off-host backup setup remain separate operational work.
